# TakeMe — автоматизация поиска работы

## Язык общения

Отвечать пользователю всегда по-русски.

## Идея проекта

Сервис, который мониторит вакансии на нескольких IT-площадках, находит подходящие
через LLM-матчинг с резюме, присылает их в Telegram с кнопками, и по нажатию
пользователя сам откликается (с сопроводительным письмом при необходимости).
Финальное решение "откликаться или нет" всегда за пользователем — это НЕ полностью
автономный автооткликер, а ассистент, который убирает рутину поиска и печати писем.

Владелец проекта — единственный пользователь (не мультитенантный сервис).

## Целевые площадки (в порядке приоритета)

1. **HH.ru** — публичный API для соискателей закрыт (с декабря 2025), поэтому
   доступ только через Playwright (эмуляция браузера с авторизованной сессией).
2. **Хабр Карьера** — есть официальный API с документированными правилами
   использования (career.habr.com/info/legal/api_rules). Нужно проверить, что
   именно доступно для отклика от лица соискателя, прежде чем писать Playwright-агент
   под неё — возможно API достаточно.
3. **GetMatch** — публичного API нет, только Playwright. Модель может отличаться
   от "классического" отклика (возможно, это скорее подписка/подборка от
   рекрутера, а не прямой apply) — нужно проверить вручную процесс на сайте
   перед написанием agent.apply().
4. **Сайты IT-компаний напрямую** (будущее расширение) — универсальный
   form-filler под типовые ATS (Greenhouse, Lever, Workday, BambooHR) плюс
   LLM-парсинг нестандартных форм.

## Архитектура

Общий абстрактный интерфейс агента + отдельная реализация под каждую площадку.
Оркестратор/планировщик не знает специфики конкретной площадки, работает
через одинаковые методы.

```
job_agents/
├── base.py            # абстрактный класс JobAgent
├── hh_agent.py         # HHAgent(JobAgent) — Playwright
├── habr_agent.py       # HabrAgent(JobAgent) — API или Playwright, TBD
├── getmatch_agent.py   # GetmatchAgent(JobAgent) — Playwright
└── company_agent.py    # CompanySiteAgent(JobAgent) — на будущее
```

```python
# base.py
from abc import ABC, abstractmethod

class JobAgent(ABC):
    platform_name: str

    @abstractmethod
    async def login(self) -> None: ...

    @abstractmethod
    async def search(self, filters: dict) -> list[dict]:
        """Возвращает список вакансий: id, url, title, company, salary, raw_text"""

    @abstractmethod
    async def apply(self, vacancy_id: str, cover_letter: str | None) -> bool: ...
```

Что общее для всех площадок (пишется один раз):
- Telegram-бот и его логика/кнопки
- LLM-слой (матчинг вакансии к резюме + генерация сопроводительных писем)
- БД и её схема
- Планировщик/оркестратор, который перебирает список агентов
- Хранение сессий логина (Playwright storage_state — json с куками)

Что специфично под каждую площадку:
- Селекторы форм/кнопок (своя вёрстка на каждом сайте)
- Парсинг карточки вакансии → в общий словарь полей
- Обработка капчи/2FA
- Формат самого отклика (кнопка+текст на HH.ru; на GetMatch и Хабре — уточнить)

## Схема БД (SQLite достаточно для одного пользователя)

```sql
CREATE TABLE platforms (
    id INTEGER PRIMARY KEY,
    name TEXT UNIQUE          -- 'hh', 'habr_career', 'getmatch', 'company_site'
);

CREATE TABLE vacancies (
    id INTEGER PRIMARY KEY,
    platform_id INTEGER REFERENCES platforms(id),
    external_id TEXT,          -- id вакансии на самой площадке
    url TEXT,
    title TEXT,
    company TEXT,
    salary_from INTEGER,
    salary_to INTEGER,
    raw_description TEXT,
    match_score REAL,          -- оценка от LLM
    match_reason TEXT,
    status TEXT DEFAULT 'new', -- new / sent_to_tg / skipped / applied
    found_at TIMESTAMP,
    UNIQUE(platform_id, external_id)
);

CREATE TABLE applications (
    id INTEGER PRIMARY KEY,
    vacancy_id INTEGER REFERENCES vacancies(id),
    cover_letter TEXT,
    applied_at TIMESTAMP,
    status TEXT               -- applied / failed / response_received
);

CREATE TABLE agent_sessions (
    id INTEGER PRIMARY KEY,
    platform_id INTEGER REFERENCES platforms(id),
    storage_state_path TEXT,  -- путь к сохранённым кукам Playwright
    last_login_at TIMESTAMP,
    is_valid BOOLEAN
);
```

`UNIQUE(platform_id, external_id)` — дедупликация "уже видели эту вакансию"
на уровне базы, не в коде руками.

## Цикл работы бота

1. По расписанию (например раз в 1-2 часа) каждый агент логинится (если сессия
   не протухла) и ищет новые вакансии по фильтрам.
2. Новые (которых нет в БД по `external_id`) прогоняются через LLM-матчинг
   с резюме → оценка релевантности + короткое обоснование.
3. Подходящие уходят в Telegram: название, компания, вилка, ссылка, обоснование,
   inline-кнопки [✅ Откликнуться] [❌ Пропустить] [✏️ Своим текстом].
4. По ❌ — статус `skipped` в БД, больше не показывать.
5. По ✅ — LLM генерирует сопроводительное письмо под вакансию, агент идёт
   на площадку и откликается через Playwright/API, статус `applied`.
6. Капча — НЕ обходится автоматически. Присылается пользователю скриншотом
   в Telegram, ожидается ручное решение и подтверждение "продолжай".

## Технологический стек

- Python 3.11+
- `playwright` — браузерная автоматизация (HH.ru, GetMatch, возможно Хабр)
- `aiogram` — Telegram-бот с inline-кнопками
- `apscheduler` — планировщик задач внутри процесса
- `sqlalchemy` + SQLite — БД
- `python-dotenv` — конфиг/секреты через `.env`, не хардкодить в код
- `anthropic` SDK — LLM-вызовы

Модели: Haiku — для простых задач вроде оценки релевантности вакансии (дёшево
и быстро), Sonnet — для генерации сопроводительных писем (баланс качества/цены).
Реальная стоимость для такого объёма (десятки вакансий в день) — единицы центов
в день, не заслуживает отдельной оптимизации на старте.

## Переменные окружения (`.env`, никогда не коммитить в git)

```
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
ANTHROPIC_API_KEY=...
HH_SEARCH_TEXT=Java          # необязательно, дефолт в config.py
```

Логин на HH — по номеру телефона и коду, руками в окне браузера (WSLg показывает
его на десктопе Windows). Логин/пароль в `.env` не храним. Сессия сохраняется в
`sessions/hh.json` (в git не коммитить).

## Развёртывание на VDS (когда дойдёт до продакшена)

- Ubuntu 22.04/24.04, 1-2 vCPU, 2GB RAM, headless — без графики
- `playwright install chromium && playwright install-deps chromium`
- Процесс держится через `systemd` (не pm2 — не нужна лишняя Node-зависимость)
- Базовая защита: `ufw` (закрыть всё кроме SSH), `fail2ban`
- Код доставляется через `git pull`, а не ручным копированием файлов
- Опционально: Docker с базовым образом `mcr.microsoft.com/playwright/python`,
  экономит шаг ручной установки зависимостей Chromium

## Важные ограничения и риски (не забывать)

- Автоматизированный сбор данных и массовые механические отклики нарушают
  пользовательские соглашения площадок — реальный риск это бан аккаунта, а не
  судебное преследование при личном использовании. Держать паузы между
  действиями, не долбить площадку.
- Капча решается ТОЛЬКО вручную пользователем, никакого автообхода.
- Разработка ведётся в WSL2 (Linux-окружение внутри Windows), не в Git Bash /
  нативном Windows — меньше сюрпризов с путями и правами, ближе к тому, как
  всё будет вести себя на VDS.
- Проект — git-репозиторий с самого начала, разработка локально в WSL,
  синхронизация на VDS через `git pull`, а не копированием файлов.
